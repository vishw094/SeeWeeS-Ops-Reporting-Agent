3. CHALLENGES FACED + RESOLUTION
--------------------------------------------------------------------------------

3.1  Alias-match was over-flagging legitimate variants as DQ-03
     Initial run reported 23 DQ-03 violations on a clean dataset.

     Root cause: my D4 (alias) branch was returning DQ-03 the moment
     the row's item_id appeared anywhere in the master, even when the
     alias's canonical resolved BACK to that same item_id. So
     "Remdesivir 100 mg" (alias) with item_id=10021 — where the alias
     canonically maps to RMD-100, which is itself an item_id=10021
     row in A.1 — was being flagged as a name/id mismatch.

     Fix: extended master_by_canonical to carry the canonical row's
     item_id and tightened D4 to:
        - alias canonical agrees with row item_id  → ALIAS_MATCH
        - alias canonical disagrees but row item_id is valid → DQ-03
        - row item_id missing/unknown → accept ALIAS_MATCH

     After fix: 124 valid / 5 DQ-01 / 0 DQ-02 / 0 DQ-03 / 0 DQ-04 —
     matches the 5 manually identified missing-UID rows in the CSV.

3.2  Pipeline segfaulted with Windows access violation on
     vectordb.add_documents()  (exit code 0xC0000005)

     Symptom: every `python src/main.py` invocation exited with
     -1073741819. faulthandler trace pointed at
     `chromadb/api/rust.py:541  _upsert` invoked from PdfRag.build().

     Isolation: calling PdfRag.build() directly from a one-line script
     worked. The crash only manifested when the project was loaded via
     `from graph import build_graph`. Bisection narrowed it to "import
     pandas (and do any DataFrame work) before chromadb's add_documents
     → crash; the reverse order → fine".

     This turned out to be a known interaction between pandas/numpy's
     allocator setup and chromadb's compiled rust client on Windows —
     not a project bug. The langsmith background uploader threads
     (firing because LANGCHAIN_TRACING_V2 was enabled with a stale key)
     amplified the timing window and made the crash deterministic.

     Multiple workarounds tried:
        a) `import chromadb` pre-warm at top of main.py — insufficient.
        b) `chromadb.PersistentClient.upsert(...)` warm-up — works but
           is heavy and brittle.
        c) Deferred pandas import inside node_dq_reconcile + lazy
           _LOOKUPS_CACHE in dq_tools — robust and zero-cost.

     Chose (c) and documented the constraint at the top of graph.py and
     dq_tools.py.

     Secondary fix in tracing.py: probe the langsmith API key at
     startup and disable tracing on failure, so the uploader threads
     don't spawn against a dead endpoint.

3.3  Chroma `.get()` access violation when purging stale chunks
     My first pass at idempotent reindex used vectordb.get(include=
     ["metadatas"]) to find chunks tagged with an older source
     fingerprint, then vectordb.delete(ids=...). Both calls crashed
     in chromadb's rust binding.

     Fix: replaced the in-place chroma API approach with a filesystem
     sentinel (chroma_db/_source_fingerprint.txt) and shutil.rmtree
     when the fingerprint changes. No chroma API call needed for the
     stale-detection path.

3.4  PyPDFLoader can't read markdown
     New project source was the Dispatch Playbook .md, not a PDF.

     Fix: PdfRag.build() now switches on extension between PyPDFLoader
     and TextLoader (covers .pdf, .md, .markdown, .txt) and raises a
     precise error for anything else.

3.5  Pandas itertuples drops attributes starting with underscore
     A `master["_name_norm"] = ...` column was inaccessible inside an
     `for r in master.itertuples(): r._name_norm` loop — itertuples
     renames such fields to positional ones.

     Fix: renamed working columns to `name_norm` / `alias_norm`
     (no leading underscore) and use straightforward attribute access.

3.6  SMTP failures took the whole pipeline down
     Original email_tools handled SMTPAuthenticationError and
     SMTPException, but a Zoho TCP timeout (WinError 10060) is a
     TimeoutError — it bypassed both handlers and propagated out of
     LangGraph as an uncaught node failure.

     Fix: added TimeoutError, ConnectionError, OSError handlers and
     a 15s socket timeout. The pipeline now treats email failure as a
     soft warning and still writes report_output.html.

5. KEY TAKEAWAYS
--------------------------------------------------------------------------------

  - Determinism is a feature, not a constraint. The audit loop only works
    because the upstream KPIs are produced by code, not the LLM. The
    AuditAgent can quote exact numbers from the dq_report and the planner
    can be held to those numbers on the retry. Putting an LLM on top of
    deterministic primitives — instead of asking it to compute and judge
    in one go — is what made Feature 1's self-correction loop converge
    in one attempt on the first end-to-end run.

  - Single-source-of-truth for derived attributes. Once sla_tier became
    a column on the reconciled DataFrame, both trend_tools and the
    AuditAgent stopped needing their own copy of the tier rules. Any
    future change (e.g., moving a medicine_type from Tier 2 to Tier 1)
    touches one dictionary in dq_tools and propagates everywhere.

  - Vectorize before optimizing further. The naive Python-loop
    reconciler would have worked fine on 129 rows but would have
    embarrassed itself on 10,000. Building it vectorized from the
    start (merge + groupby + value_counts) costs the same lines of
    code and stays fast at scale.

  - Cache the slow boundary calls, not the fast ones. The biggest
    speedup came from caching the single ContextAgent LLM call by
    source fingerprint — the actual DQ + trend code already runs in
    sub-100ms; throwing more caching at it would not move the needle.

  - Native-library order matters on Windows. The pandas-vs-chromadb
    interaction is environment-specific and not a code bug in the
    classic sense, but the fix (deferred imports + lazy module-level
    pandas work) is a generally-useful pattern: never do heavy
    side-effecting work at module import time if you don't have to.

  - Graceful degradation > hard failure. Wrapping every external
    boundary (SMTP, LangSmith, chromadb's flaky `.get()`) in narrow
    try/except with a clear console message means a flaky environment
    never destroys a successful pipeline run.

8. CROSS-PROJECT MERGE — adopting the stronger ideas from a peer build
   (2026-05-21)
================================================================================

A second SeeWeeS implementation (seewees-dispatch-ai-agent-main/) was added
to the workspace for comparison. After a file-by-file review, four of its
ideas were genuinely stronger than ours and were ported in — while keeping
our wins (vectorized DQ, business_context caching, per-node timing, the
LangSmith key probe, and the Windows pandas/chromadb crash handling).

8.1  Deterministic audit + structured-JSON planner  [strongest grading win]
     - PLANNER_PROMPT now returns strict JSON:
         recommended_buffer_pct, escalation_required, cited_rules,
         dispatch_plan, what_to_monitor, contingency_triggers,
         expected_kpi_impacts.
     - run_planner_agent parses that JSON (with a `_extract_json_block`
       fence-tolerant parser and a safe fallback draft).
     - graph.apply_deterministic_audit_checks() layers HARD checks on top of
       the LLM audit verdict:
         * recommended_buffer_pct must equal the §5.2 mapping for the current
           weather risk_score (0->0, 1->10, 2->25, 3->40)
         * escalation_required must be true when risk_score == 3
         * cited_rules must be non-empty
       The audit now passes only if the LLM passed AND no deterministic
       violation fired. This makes the self-correction loop verifiable
       instead of vibes-based.
     - node_planner stores the structured draft + a rendered text version
       (dispatch_plan) for the report. Our existing retry loop, route_audit,
       human_checkpoint, and MAX_AUDIT_RETRIES are untouched.

8.2  RAG retrieval evaluation  [new measurable capability]
     - New src/tools/knowledge_tools.py with a 5-question eval set tied to
       playbook sections (DQ rules, buffer policy, alias table, SLA classes,
       reporting requirements).
     - run_rag_eval scores recall_at_k (expected section heading appears in
       top-k) and grounded_answer_accuracy (all expected terms appear).
     - node_pdf_context runs it every run and prints:
         [RAGEval] Recall@5=1.0 grounded_accuracy=1.0
     - Required section-aware markdown indexing (see 8.4).

8.3  Deep-dive analytics appendix  [richer Idea-3 output]
     - trend_tools gained compute_item_spikes() (planning-window volume vs
       historical daily baseline) and compute_deep_dive_tables()
       (daily valid units, corridor-by-day, correction/exclusion breakdowns,
       sample corrected + unresolved rows).
     - graph renders these as an HTML appendix appended to the report AND a
       plain-text appendix (report_appendix.txt) emailed as an attachment.
     - email_tools.send_email_smtp now supports file attachments.

8.4  Section-aware markdown RAG + lazy LLM init  [supporting changes]
     - pdf_tools splits markdown by heading, tags each chunk with
       section_title + stream (policy/reference), and uses larger chunks for
       reference/table sections. Added PdfRag.retrieve(..., stream=...).
     - agents.py switched to a lazy _get_llm() so the module (and graph.py)
       imports without OPENAI_API_KEY — which is what unblocked pytest.

     - seewees-dispatch-ai-agent-main/outputs/sample_report/
       "Gmail - MSBA Ops Multi-Agent Dispatch Report.pdf" is a screenshot/
       export of an actual Gmail message. Their README says it is redacted;
       confirm no real recipient email address / PII remains before sharing.

9.4  Analytical (train/test) leakage — CLEAN
     - There is no ML model training in the pipeline (the old IsolationForest
       path was removed), so classic train/test contamination does not apply.
     - The one place a baseline meets a "test" set is the item-spike and PoP
       analysis. Verified the partitions are strictly disjoint:
         * planning window = planning_day in {Day0, Day1}
         * historical baseline = planning_day == History
       The historical daily average is computed ONLY from History rows; the
       planning-window counts never feed the baseline. No future->past leak.
     - PoP analysis splits History alone by date midpoint; planning rows are
       excluded entirely.
     - Caveat (not leakage): the RAG eval set is small (5 questions) and its
       expected answers are hand-authored, so Recall@5=1.0 is indicative of a
       small, well-structured playbook — treat it as a sanity check, not a
       rigorous benchmark.
